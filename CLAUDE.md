# Statera Contracting — Project Context

Calgary renovation contractor. Next.js 16 App Router, React 19, Tailwind, deployed to Vercel. Service area: Calgary, Bearspaw, Rocky View County.

## BabyLoveGrowth content import

Statera uses BabyLoveGrowth (AI SEO content generator) on the API integration method. This is a manual import workflow, not a live feed. Confirmed with BabyLoveGrowth support:

- Their "Publish" button does not push anything live. The API's `published` field never flips to true from their side.
- The only way an article goes live is: fetch it, add it to `lib/posts.ts` by hand, deploy. Their crawler then finds the URL in our sitemap and flips their dashboard to "published" a day or two later, as a confirmation, not a trigger.
- There is no auto-publish path for a custom Next.js site on this integration type — going live always means fetching the article and adding it to `lib/posts.ts` ourselves. As of 2026-08-06 that step is fully automated with no human read required first (see "Automated daily publish" below).

Fetch a specific article with:

```
npx tsx scripts/import-babylovegrowth-article.ts <articleId>
```

This prints a `Post` object (sanitized HTML) ready to review and paste into `lib/posts.ts`. As of 2026-07-15, links off the Statera domain are kept live rather than stripped, see `lib/babylovegrowth.ts`'s header for why. It does not publish anything itself.

### Automated daily publish

As of 2026-07-14, this runs unattended, no manual "please fetch this" request needed day to day. Mauricio has opted into full automation on the mechanical items below.

Decision 2026-08-06: the comparison/listicle trip-wire (title patterns like "top N", "vs", "alternatives", "best ... companies/contractors/providers") was removed at Mauricio's explicit direction. He was told this means comparison-title pieces publish with no review, including "Top N companies/alternatives" listicles that name competing contractors on Statera's own blog — the same category of SEO/reputational risk already accepted for outbound links on 2026-07-15. He chose to accept it, on the basis that the articles published so far have been good enough and are generating good traction. Do not reinstate the trip-wire without him asking.

The 1/day publish cap (created 2026-07-16 after a backlog flush fired six webhooks in eight minutes and published four articles with no review) is still in effect, and as of 2026-08-06 it's a **hard cap: never more than one article published per UTC day, no exceptions**, with the article to publish chosen by matching BabyLoveGrowth's content calendar. Mauricio confirmed BabyLoveGrowth's own generation sometimes runs a day or two ahead of the calendar (an article can be fetchable via the API before its calendar slot arrives) — that's expected and not a reason to publish it early. Concretely:

- **Never publish an article ahead of its calendar-scheduled date**, even if it's already fetchable via the API (webhooks fire near `created_at`, well before the calendar slot, sometimes a day or two before). If an article's scheduled date is later this week, leave it `"queued"` and let a later day's run pick it up.
- **Determining the calendar-scheduled date**: the API exposes no such field (checked: `id`, `title`, `created_at`, `updated_at`, `published`, `keywords`, etc. — nothing else). Two sources, in priority order: (1) a date Mauricio has confirmed by sharing a calendar screenshot — treat as ground truth, note in the state file that it's confirmed; (2) absent that, estimate `created_at + 3 calendar days` — cross-checked against 9 confirmed dates as of 2026-08-06 and correct in 8/9. Mark estimated dates as such in the state file reason so a future confirmed screenshot can correct them.
- **Backlog that's already overdue** (estimated/confirmed calendar date already in the past) still only publishes one at a time — pick the oldest by article ID, dated (in `lib/posts.ts`'s `date` field) to its original estimated/confirmed slot rather than the day it actually got committed, and queue the rest for subsequent days. The state file's `publishedAt` should still be the real commit date, for bookkeeping.
- **If more than one article's calendar date lands on the same day** (or a same-day new arrival collides with overdue backlog), that's still only one publish today: pick the oldest by article ID, queue the other(s) — the cap wins over exact date-matching in that rare case, since Mauricio wants pace kept to exactly one per day above all else.

Do not loosen this back to "publish immediately regardless of calendar date" or "publish more than one per day" without Mauricio asking.

This runs as a Claude Code cloud routine (Routines → Statera BabyLoveGrowth Daily Publish), on Anthropic-managed cloud infrastructure, so it works even when nobody's machine is on. As of 2026-07-15 the routine has two triggers:

- **API trigger (primary)**. BabyLoveGrowth's webhook fires the moment an article is finalized on their end, confirmed with their support: this happens before any manual publish step on our side and doesn't depend on our sitemap being crawled, which is the reliable "this article is really done" signal the old polling approach never had. Their webhook can't call the routine directly (it requires a beta header their wizard has no way to set, and its body only accepts freeform text, not their article JSON), so it posts to a relay at `app/api/babylovegrowth-webhook/route.ts` on this site. That route checks BabyLoveGrowth's bearer token against `BABYLOVEGROWTH_WEBHOOK_SECRET`, then fires the routine via `https://api.anthropic.com/v1/claude_code/routines/{id}/fire` using `CLAUDE_ROUTINE_TOKEN`, passing the article's ID and title as the run's `text` context. This depends on BabyLoveGrowth's "Automatically Publish" toggle (Settings → Integrations) staying on, if it's ever off, their own dashboard Publish button becomes the gate again and the webhook only fires when a human clicks it over there.
- **Schedule trigger (fallback)**. Runs daily as a backstop for a webhook delivery that's missed, delayed by relay downtime, or dropped. It starts with no specific article in mind, so it falls back to listing all articles and diffing against the state file.

If the relay can't reach the routine (routine paused, token rotated, etc.) it emails mauricio@mrwebsolutions.ca via Resend and logs the failure in Vercel. That's the only proactive signal a webhook delivery failed; the daily schedule trigger will still catch anything missed within 24 hours regardless.

State tracking: `.automation/babylovegrowth-seen.json` in this repo's root, a JSON object keyed by article ID, value `{"status": "published", "publishedAt": "YYYY-MM-DD"}` or `{"status": "queued", "reason": "..."}` for an article whose calendar-scheduled date hasn't arrived yet (the reason should say whether the date is confirmed via screenshot or estimated via `created_at+3`). (Older entries from before 2026-08-06 may still show `"held"` from the trip-wire era — those have been drained to `"published"` since that policy no longer applies; that status is no longer produced going forward.) Check this file before processing an ID a second time, even one delivered by the webhook, this is what stops a retried webhook delivery or an overlapping schedule run from double-publishing. It lives inside the repo (not on a local machine) on purpose: a cloud routine gets a fresh checkout each run, so state has to be committed to persist. Commit updates to this file in the same commit as any content change.

New-article detection: when a run starts with a message naming a specific "Article ID" (the webhook path), fetch it directly, skip the list step, then apply the calendar-date + hard-cap logic above (publish now only if today's slot is still free and this article's date is today or already past; otherwise queue it). When a run starts with no specific article (the daily schedule fallback), list the full article set, treat every ID not yet in the state file as a candidate, and apply the same logic — even if several candidates are simultaneously past-due, still publish only the single oldest-by-ID one and queue the rest, the hard cap applies the same way regardless of trigger type. Either way, do NOT filter on `published`. Per BabyLoveGrowth support, that field only flips true after we've already published something ourselves and their crawler confirms it off our sitemap days later, it is a confirmation, never a trigger. Confirmed 2026-07-14: fetched an article whose created_at and updated_at were under a second apart (as fresh as it's possible to catch one) and its content_html was already complete (17k+ characters, properly closed, not truncated). Their system evidently only creates the article record once generation has finished, it doesn't stream partial content into a record while a job like the dashboard's "GENERATING... ready by [time]" countdown is running. No same-day buffer is needed on the fallback path either.

Mechanical fixes, apply automatically, publish the same run — these are quality fixes, not gates:

3. Byline: any first-person "what I've learned" style section must be attributed to Patrick, never Mauricio. Fix if blank, unclear, or wrongly attributed.
4. Company name: "Statera Contracting" is always two words in body text and visible link text. One word only inside an actual href/domain.
5. Missing-word generation bug: sentences with a dropped subject or clause, often visible as a stray double-space or a sentence starting mid-thought. Fill the gap based on context, this is a known BabyLoveGrowth generation defect, not a reason to hold.
6. Spelling/typos introduced by the generator.
7. Drop the article's opening image if it duplicates `coverImage`, the page template already renders that above the content.
8. Decision 2026-08-06: competitor links get unlinked, not left live and not deleted. If content names or links another business that competes with Statera for the same renovation/contracting work (e.g. a "Top N companies/alternatives" listicle profiling rival contractors, or a "sources" citation to one), remove the `<a href>` wrapper but keep the visible text as plain text — don't delete the sentence/bullet, don't hold for review. This is narrower than the outbound-link policy from 2026-07-15: links to industry associations, building codes, government sites, material manufacturers, mortgage advice, or similar non-competitor citations stay live as before (`rel="nofollow noopener noreferrer"`, `target="_blank"`); only links to businesses that compete with Statera get unlinked. BabyLoveGrowth's own reciprocal attribution link (`babylovegrowth.ai`) is not a competitor and stays live.

Note every mechanical fix actually applied in the commit message so there's a record, even though nobody has to approve it first.

Once mechanical fixes are applied and the calendar-date + hard-cap check above says this one publishes now, add the post to `lib/posts.ts` — set its `date` field to the article's calendar-scheduled date (confirmed or estimated), not the day it's actually being committed — run `npx tsc --noEmit` and `npm run build` to confirm it's valid, then commit and push to a `claude/`-prefixed branch (the routine can't push to `main` directly), and open a pull request against `main` with `gh pr create`, titled exactly `[BabyLoveGrowth Auto-Publish] <article title>` (or `[BabyLoveGrowth Auto-Publish] hold: <article title> (build failed)` if `tsc`/`build` fails — that's the one case still worth holding for, since broken content shouldn't ship — still no lib/posts.ts change, just the state file, and do notify Mauricio for that case, or `[BabyLoveGrowth Auto-Publish] queue: <article title>` for one deferred by the cap or not yet at its calendar date, still no lib/posts.ts change). A GitHub Action (`.github/workflows/babylovegrowth-automerge.yml`) auto-merges any PR with that exact title prefix from a `claude/` branch, no human review needed, that title tag is reserved for this routine, don't reuse it elsewhere. Mark the state file entry `"published"` with today's actual date as `publishedAt` (separate from the cosmetic `date` field in `lib/posts.ts`), or `"queued"` with the reason as set above. **Exactly one article publishes per run, ever** — even a schedule-fallback run that finds several past-due candidates only publishes the single oldest one and queues the rest for subsequent days; that's how the hard 1/day cap is enforced. One PR per publish.
